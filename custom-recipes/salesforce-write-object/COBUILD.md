- Use this recipe to create or update Salesforce records from one DSS input dataset. Salesforce datasets are read-only; configure the remote destination with `object_name` rather than using a Salesforce dataset as the recipe output.
- Bind the source dataset to `incoming_dataset_name` and a writable DSS result dataset to `main`. Both roles are required. The result dataset is an operation log, not a copy of the Salesforce object; agree on its destination with the user.
- Select an accessible preset matching `auth_type`: `oauth` uses the `oauth` parameter from `oauth-credentials`; `oauth_sandbox` uses `oauth_sandbox` from `oauth-sandbox-credentials`; `oauth_client_credentials` uses `oauth_client_credentials` from `oauth-client-credentials`; `oauth_jwt_bearer` uses `oauth_jwt_bearer` from `oauth-jwt-bearer`.
- Use presets as opaque references. If authentication is incomplete, ask the user to finish setup in DSS settings; do not request tokens, passwords, client secrets, or private keys in chat.
- Set `object_name` to the exact Salesforce object API name, such as `Account`. Input column names must match writable Salesforce field API names. Prepare the input to contain only intended fields; every column except `Id` is sent in the request.
- Each input row with a missing or null `Id` creates a record. A non-null `Id` updates that exact record; an empty string is not treated as missing. This is not an upsert by external ID, and there is no append, overwrite, or delete mode. Resolve ambiguous create/update intent before execution.
- Each row produces `operation`, `error`, `salesforce_record_id`, and `data` in the DSS output. Inspect `error` before reporting success: Salesforce HTTP errors can be logged per row without failing the recipe.
- Execution changes Salesforce records and can partially succeed. Do not run or automatically retry it unless the user's request authorizes those writes; retrying rows without `Id` can create duplicates.
